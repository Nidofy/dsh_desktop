# Electron 迁移补充：持续跟随官方引擎与后续开发

> 2026-09-29 更新：持续演进原则继续适用；当前基线、排期与升级演练见[基于 0.2.0-rc.1 的迁移计划](ELECTRON-MIGRATION-PLAN-0.2.0-rc.1.md)。本文的 `477b4f4` 为历史研究样本。

日期：2026-09-28。补充 [迁移总方案](ELECTRON-MIGRATION-ANALYSIS-2026-09-28.md)。本文给出后续实施设计，不表示升级流水线、接口或门禁已经实现。本轮沿用已取得的官方 `477b4f4` 源码基线，没有切换产品分支、升级引擎或迁移数据。

## 1. 先确定长期维护的目标

**迁移的完成条件应增加一项：在保留内网、热切换和工程保护行为的前提下，能够按固定流程再次升级官方版本。** 仅在某个官方版本上跑通全部功能，仍可能重新形成旧版的升级锁定。

建议采用“官方整套发行组合持续集成 + 小范围适配层 + 自有功能模块”的维护方式。官方负责 Agent、Session、工具执行与客户端主体；派生版负责发行策略、连接治理、工程保护和自身体验。新功能持续开发，上游升级在独立候选分支验证，通过后合回同一产品主线。

“跟随官方”有三个独立动作：观察官方变化、验证升级候选、向用户交付新版。可以经常观察并验证，但内网终端只安装已验收的完整离线包；不需要现场联网更新，更不需要每个 alpha 都立即交付。

## 2. 源码事实决定升级单位

官方 `apps/desktop/src/release.ts` 用一个 release 描述 shell 与 bundled DSH 的版本，并绑定 Host 协议、Node 和 pnpm。`core-package-set.ts` 校验 DSH/Host 包版本与预期发行版本；`runtime-tree.ts` 记录目标平台和文件完整性。因此默认升级单位是经过验证的 **Electron 壳 + Host + DSH/Core plugins + Web client + 运行时依赖**。

不建议首版支持用户任选引擎版本、单独覆盖 node_modules、原地替换 Host 或运行中升级引擎。连接热切换与引擎升级是两种机制：前者保持进程与请求租约，后者需要排空/停止任务、完整切换发行组合、重新启动。

源码入口：[release.ts](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/apps/desktop/src/release.ts)、[core-package-set.ts](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/apps/desktop/src/core-package-set.ts)、[runtime-tree.ts](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/apps/desktop/src/runtime-tree.ts)。

另外，本轮补读确认 Desktop 的 `19387` 是默认端口，官方文档允许 `webserver.config.port` 覆盖。并存隔离应先通过 profile 实现并验证，只有不能满足动态端口/启动回执要求时才新增 Host 补丁。来源：[官方 Desktop README](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/apps/desktop/README.md)。

## 3. 迁移时建立六个边界

| 边界 | 官方拥有 | 自有代码拥有 | 约束 |
|---|---|---|---|
| Agent/Session | 循环、压缩、工具调用、持久化和迁移 | 任务关联、审查数据、保护状态 | 不复制第二套循环/会话 writer；自有元数据单独存储 |
| 服务/API | Cordis 服务、事件、官方 RPC | 窄适配 facade 与运行时校验 | 业务模块不遍历官方对象树或直接访问私有字段 |
| 模型连接 | 原生 adapter 与模型调用 | connection ID、修订、凭据 lease、工作区外发策略 | 不另造绕开原生审批/上下文链路的模型请求引擎 |
| 客户端 | 会话 UI、composer、原生 slots | 工程面板、设置、草稿追加 adapter | DOM/内部组件依赖集中到一个客户端适配模块 |
| 桌面宿主 | Main/Host 生命周期、认证通道 | 发行策略、凭据/文件保护窄平台服务 | 不重新维护 Tauri 监督协议和第二套 Host supervisor |
| 发行/依赖 | 官方打包和运行时描述机制 | 独立身份、离线材料、发布准入与回执 | 不删除上游完整性检查来迁就版本号或缺失依赖 |

“公开接口”在预稳定项目中也可能变化。适配层的作用是集中变化、缩小回归范围，不是让任意新引擎天然兼容。

建议只建立已有消费者需要的契约，例如：

- `ConnectionPort`：准备/应用/查询修订、获取请求 lease、退休修订。
- `TaskPort`：查询任务事实、订阅状态、取消、检查退出影响。
- `ExecutionPort`：使用 DSH 的审批和执行后端运行工程动作，返回任务/作业身份。
- `DraftPort`：按会话和草稿修订追加内容，返回幂等确认。
- `ProtectionPort`：取得/继承/释放文件保护 lease、恢复预检。
- `PlatformPort`：受限的凭据、打开/定位/保存文件操作。

这些是拟议自有接口名，不是官方现成 API。能力已经能直接通过稳定性较好的公开服务表达时，无须再加一层无意义的封装；只在确实存在耦合的边界做转换。

### 适配失败按能力处理

连接凭据、认证、网络策略或已启用的严格保护无法确认时，阻止受影响执行，但尽可能保留本地浏览、设置和导出。主题、桌宠、只读诊断不兼容时可单独停用。出现未知会话格式时拒绝写入；可导出原文件，不能伪造空历史或静默修复。

任务状态显示“未知”和“已停止”必须区分；不把 observer 断线解释为可以安全升级。取消回执、实际进程结束和远端副作用是否发生也分别处理。

## 4. 将上游耦合从文件清单变成可执行契约

现有 `HARNESS_ADAPTER.md` 已有耦合清单，应继承其诚实记录方式；当前精确版本/hash 准入也有价值。但散落的精确版本判断要逐步集中，不能每次升级全仓替换版本字符串。

建议按依赖性质分级：

| 等级 | 示例 | 升级策略 |
|---|---|---|
| A：官方公开配置/服务 | profile、Settings、credential seam、RPC | 类型/schema 检查 + 行为合约；不假定 semver 兼容 |
| B：官方内部接口 | UI 内部对象、任务投影字段、Host 私有协议 | 只允许适配模块导入；每轮升级做定向源码审查和集成回放 |
| C：自有上游补丁 | catalogProvider、payload hook、发行入口 | 补丁台账 + 定向测试 + 退役条件；优先寻求上游等价扩展点 |
| D：文本/DOM/构建产物锚点 | 英文 prompt 前缀、CSS 提取、DOM 选择器 | 优先移除；临时保留必须精确匹配并失败可见，禁止宽松匹配兜底 |

新增功能不得从 A/B 无记录地滑向 C/D。M0 给每个依赖一个 ID，关联官方文件/符号、消费者、可观察行为、测试和风险；CI 对自有业务目录执行依赖方向检查，禁止直接导入已列入限制的官方内部路径。

契约不只检查“字段还在”。例如：`turn/end` 的时机可能变化；同名设置字段可能换单位；模型名不变但 reasoning/input/cache 能力变化；取消先回 ACK 还是等终止也会影响保护与升级。必须用真实 Host/adapter 的合成场景测这些行为。

### 两项现有补丁的长期策略

**目录继承补丁**只解决“独立连接路由继承完整模型目录”。将路由身份、catalog source、模型 override 的行为固定为测试，官方出现等价机制后替换。不得因路由可以注册，就忽略模型兼容字段是否完整。

**payload hook 补丁**只保留必要的按请求作用域；先迁只读观测，修改 payload 的缓存实验独立启用。官方 hook 若语义不同，比较真实 wire、缓存作用域和日志重建能力后再替换。不能因为名称相似就删除旧补丁。

通用且适合上游的 hook/配置扩展可以准备上游贡献；品牌、内网策略与个人业务功能保留在自有层。上游接受不是本地交付的前置条件。提交外部 PR/推送仍是独立操作，本文没有执行。

## 5. 版本与兼容性：记录“已验证组合”

建议新增机器可读兼容记录，以下是字段设计，尚未创建产品配置：

```text
ReleaseCombination
  productVersion / distributionRevision / channel / target
  upstreamTag / upstreamCommit / integratedCommit
  officialReleaseVersion / desktopHostProtocolVersion
  electronVersion / nodeVersion / packageManagerVersion / lockDigests
  adapterContractVersion / extensionVersions / patchIds
  sessionWriterVersion / supportedImportSources
  ownedDataSchemaVersions / networkPolicySchemaVersion
  packageManifestDigest / qualificationReceipt
```

`upstreamCommit` 表示采用的官方来源；`integratedCommit` 表示包含自有改动的可取得源码。两者不能混为一谈。第三方模型 SDK、目录和原生组件的版本也在锁定依赖/材料清单中保留，不能在现场动态漂移。

产品展示可分别显示“自有产品版本”和“基于 DSH 某版本”。官方现有 release 等值校验需要保留：默认内部配套包继续按一套已验证版本构建，自有发行号另存 distribution metadata。若安装器要求独立产品版本，应一次性设计显式的产品版本—官方版本映射并覆盖所有验证点，不能任意改一个 package.json 后跳过不匹配错误。

兼容性声明采用两个维度：运行组合兼容、旧数据可导入。首发只支持一个当前运行组合，保留前一合格发行包及其数据回退说明；迁移 fixture 则覆盖实际支持的旧数据来源。不为每个历史引擎永久保留运行适配器。

功能探测用于解释与降级，精确来源/整包准入用于决定能否运行。Host 协议版本相同或 smoke 成功，都不能单独证明组合兼容。插件 peer range 也不能用 `*` 掩盖问题。

官方已有插件 peer 兼容检查和按精确版本记录的豁免。正常发行门禁不依赖风险豁免；已安装的不兼容第三方插件应保留文件、明确停用/待升级，必需自有插件失败则阻断对应能力。来源：[插件兼容契约](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/boot/plugin-manager/README.md)。

## 6. 仓库和分支如何长期维护

建议以官方 monorepo 的 fork 作为 Electron 产品唯一开发仓库，保留 upstream remote。既有 Tauri 仓库冻结为来源/历史交付，避免迁移结束后每个功能仍跨两个仓库改三套版本。

```text
upstream 发布 tag U0 ──────────────→ U1
          │                         │
产品 main：U0 + 自有模块 ─→ 升级候选：合入 U1 + 适配
          │                         │通过门禁
          └─ 普通功能分支 ──────────→ 产品 main → 自有发布 tag
```

- `main` 保存可构建的集成代码；用户安装的是合格发布 tag/包，而非任意 main commit。
- `codex/upstream-<目标版本>` 从当前产品 main 创建，在隔离 checkout 合入固定上游提交；共享主线不强推重写历史。
- `codex/feature-<功能>` 从当前集成基线开发；若触及升级中的同一适配边界，先统一契约再合并，避免两边分别改官方内部文件。
- 发布包使用自有不可变 tag；安全修复可从当前发布 tag 建短期维护分支，验证后同时进入升级候选，避免回归。

主方案中的 `codex/electron-intranet` 是迁移期间的工作分支名；迁移通过后应明确它与产品 main 的关系，不长期保留两条新功能主线。

Git 提交是补丁的唯一事实来源，台账只是索引。不要同时维护容易漂移的“改过的源码”和另一套手写 patch 文件；需离线传递补丁时从已固定提交生成，并记录校验值。

## 7. 每次官方升级的标准流程

| 步骤 | 动作 | 退出条件/产物 |
|---|---|---|
| U0 发现与选择 | 读取官方 tag/release/security 信息，判断是否采纳 | 固定目标 SHA、目的和影响等级；没有浮动 latest |
| U1 影响报告 | 比较当前 upstream SHA 与目标；映射耦合台账、依赖锁、数据和外联变化 | affected-contracts、迁移要求、补丁保留/删除/改写清单 |
| U2 隔离集成 | 独立 checkout 合入目标，解决补丁冲突 | 可取得 integrated commit；原日用包和数据不变 |
| U3 类型与契约 | 编译、schema/导入检查、真实 Host 合约测试 | 必需契约通过；未知能力清单明确 |
| U4 行为差分 | 旧/新候选分别对同一 mock 场景回放 | 连接、工具、审批、缓存、取消、保护语义逐项对照 |
| U5 数据升级 | 用支持来源的 fixture/副本验证读/写迁移和中断恢复 | 原数据不变；新格式可恢复；未知版本拒绝 |
| U6 完整打包 | 构建整套 runtime、许可/材料清单、完整性和离线验收 | 新包与 qualified commit 对应；不复用不匹配旧回执 |
| U7 试用与推广 | 独立候选数据根、样例工程、必要现场验证 | 风险接受记录和实际包证据；再发布到自有通道 |

用户端收到的是 U7 后的整包；内网包随附 offline verification、兼容清单、升级说明和回退数据要求。已在途任务需按官方生命周期协调，更新失败不能损坏旧完整目录。

### 影响等级与节奏建议

| 变化 | 建议处理 |
|---|---|
| 仅文档或不进入运行包的工具 | 不要求重新发布桌面；确认确实不改生成物 |
| UI/只读辅助功能 | 受影响测试 + 基础内网/启动门禁，合格后随下一批交付 |
| 模型 SDK、工具执行、审批、网络、认证、沙箱 | 升级候选高优先级，真实协议和负向场景必测 |
| Session/数据库/Host 协议/Node ABI | 按完整迁移处理，重新打包和目标平台验证 |
| 与当前发行实际相关的安全修复 | 优先验证升级；不能及时整体升级时评估最小回移及依赖，不能仅看补丁应用成功 |

维护建议为每周评估一次上游、每 2–4 周在有合格改动时发布一批；这只是排期建议，不是已创建的自动检查。关键问题不受固定周期限制。允许跳过无价值的 alpha，但跳版本要检查完整的中间迁移链和发行说明，不能只测试最近两版。

## 8. 让升级测试可重复，而非每次人工重验全部功能

现有 `check-harness-upstream.ps1` 主要读 refs、ahead/behind、recent tags 和部分目录 diff，且面向旧双仓库 pin。可保留为来源检查起点，后续应扩展为机器可读 impact report；不能将它当前的输出视为“升级兼容通过”。

建议分层建设以下门禁，名称是实施任务，不是已存在命令：

1. **组合检查**：来源 SHA、锁、Host 协议、必需插件、schema 和发行策略；生成配置，避免多个地方手填版本。
2. **依赖边界检查**：业务模块只能通过声明的端口访问内部服务；统计新增加的 B/C/D 耦合。
3. **真实 Host 合约**：最小 profile 启动、鉴权、事件、草稿、路由回执、终止状态；不只用 mock 对象测自有代码。
4. **两协议行为回放**：同名模型、暂停流、更换 Key、重试、策略撤销、取消、子任务与后台作业；比较允许变化与必须不变项。
5. **持久化 fixture**：旧 writer 生成的真实格式样本、未知未来格式、重复导入、磁盘满/中断恢复；记录 writer 来源。
6. **打包环境检查**：实际 EXE、无全局开发运行时、空缓存、外网阻断、可选插件不兼容、与官方版并存。

模型输出通常不确定，不能拿自然语言逐字相等判断兼容。用固定 mock 验证协议与状态，用相同样例和预算做少量真实模型质量评估；真实请求只在批准的服务/测试资料上运行，不自动消耗个人订阅。

上游测试证明官方行为，自有合约证明增量行为，二者都需要。最终发行固定执行不可省略的内网、凭据、热切换、数据与保护门禁；普通功能提交按影响范围测试，避免每次纯 UI 文案改动都重跑整套现场验收。

## 9. 数据兼容是长期开发的一等约束

Session 格式、工作区数据库、自有连接配置、诊断/快照元数据和 OS 凭据分别版本化，不能只看 DSH 包版本。上游已存在相邻 Session 代际迁移设计；自有插件应通过官方 reader 得到逻辑事件，不自己解析所有历史 JSONL 版本。

本次官方 tag 中 writer 常量为 4，而 `session-format-status.md` 的公开记录仍列出 released 3 并要求核实发布新鲜度。这说明即使有机器文档门禁，也不能盲从一个旧发布字段；应交叉核对目标 tag 的 writer、迁移链及发布证据。来源：[格式状态](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/session-format-status.md)、[writer 常量](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/session/src/types.ts)。

自有数据库以官方 task/session ID 为关联键，记录必要 source revision；不要复制一套“真实任务状态数据库”并独立驱动执行。缓存投影可重建，用户标注与保护记录不可当缓存丢弃。

升级前区分可只读打开与首次续写升级；在首次写入前完成相应备份/journal。多版本并行使用独立活动根，不能两个引擎写同一 profile/database。数据回退使用旧包和升级前副本，新任务及外部工程修改须另行审阅合并。

## 10. 后续新增功能的开发规则

每项新功能先回答：由谁执行、访问哪些资料/网络、是否写持久数据、依赖哪项官方契约、失败影响哪些能力、怎样在下次上游升级中验证。形成一页设计即可，不需要大而空的框架文档。

| 新功能示例 | 推荐开发方式 | 要避免的升级成本 |
|---|---|---|
| 新模型协议或提供方 | 原生 adapter 支持优先；连接配置/能力层增量，协议 fixture 配套 | 为一个服务复制 Agent Loop，或把订阅身份当普通 API Key |
| 工程面板、Hg 写操作 | 自有 engineering service + DSH 审批/执行 + UI slot | 直接在 renderer 执行任意 shell |
| 智能诊断/A-B | 观测与修改请求分离；修改请求明确实验版本 | 只读开关改变模型 prompt，无法定位升级差分 |
| 更强快照保护 | ProtectionPort + 平台 helper + 写操作准入覆盖 | 每个功能各自加一套快照 hook，彼此覆盖不清 |
| 新桌面布局 | 优先官方 slot/组件扩展；临时 DOM adapter 集中 | 大面积复制官方会话页面，使每次 UI 更新都手工搬运 |
| Codex/其他后端 | 先交接任务；确需执行接入时独立 backend capability | 把外部后端的工具/审批冒充 DSH 原生工具状态 |

开发时优先查官方近期是否已有同类功能。上游补齐后按“对照行为 → 保留数据迁移 → 删除重复实现”的路径收敛。删除旧扩展应比长期维持两套实现更容易，才算边界设计有效。

新功能若确实需要官方内部接口，可以接受有边界的技术债，但必须附升级触点、合约测试和替代条件。不要为“零 fork 补丁”牺牲关键行为，也不要为方便把任何功能都塞入 Main 或 observability。

## 11. 将长期适配纳入当前迁移排期

| 原阶段 | 增补交付 |
|---|---|
| M0 | 耦合台账、来源/组合 manifest 设计、两项补丁退役标准、适配层边界、升级演练版本选择 |
| M1 | 发行策略注入点、独立版本元数据、profile 优先的身份/端口配置、外联回归入口 |
| M2 | ConnectionPort 与 lease 行为合约、实际状态查询、schema 迁移 fixture |
| M3 | Task/Execution/Draft/Protection 适配、子任务/并发保护合约、OS helper 协议 |
| M4 | 可选模块降级、诊断 schema、移除不必要 prompt/DOM 耦合 |
| M5 | 至少一次真正的“旧官方组合 → 新官方组合”隔离升级演练，产物、数据与回退证据齐全 |

新增 `UPG-01` 门禁：在首次正式迁移发布前，用两个已公开且可取得的官方版本完成演练，无须等待未来发布。将自有关键垂直切片先适配到较早样本，再迁到目标版本；覆盖至少连接、保护、数据和打包。该样本只证明这些边界可升级，不代表将来所有版本自动兼容。

新增 `UPG-02`：必需插件不兼容必须明确阻断对应执行，可选插件停用可解释；不得用兼容豁免通过正式 Gate。

新增 `UPG-03`：同一组合 manifest 可从干净构建环境生成可核验运行包，来源无需依赖开发机残留目录。签名/时间戳等不确定项单独记录，不把“可重复取得输入并验证输出”夸大为所有安装包逐字节一致。

相对原 36–60 人日估算，组合/台账/升级差分自动化和一次演练建议额外预留 **5–9 人日**；原方案已有适配与测试工作不重复累计。修订为 **41–69 人日**，加 20% 不确定性约 49–83 人日，M0 后再校准。

长期维护先按每个常规升级 1–3 人日、涉及格式/协议/原生运行时升级 4–8 人日做资源预留，属于规划假设，须用首次两次演练/升级实测替换；重大重构可能超出该范围。首三轮可预留约 20%–30% 开发容量用于上游适配，再依据实际成本调整。

记录的维护指标应包括：距已评估官方发布的滞后、上游补丁数量与存活期、B/C/D 耦合数量、升级修复耗时、数据/网络回归问题、必需门禁未知项。若连续升级都要改大量业务模块，应优先修边界；合并冲突数量少不代表行为兼容。

**迁移验收应同时证明“这一版好用”和“下一次升级有可重复的路径”。** 后续开发围绕同一套边界和门禁增量扩展，才能持续吸收官方主引擎能力而不再冻结在某个 fork 提交。
