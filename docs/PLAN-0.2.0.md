## 实施顺序

1. rc1：连接基础、持久状态、Project Actions、通知、产物、任务基线、Git/Hg 只读变更。自检与前缀测试同步建设。
2. rc2：安全恢复、异常恢复、ProviderCapabilities、Cache Probe、前缀定点修复。
3. rc3：自检集成、迁移回退、完整包、部署与故障验证。
4. stable：对同一候选构建逐项审计，发布准确的适用范围、证据、已知限制。

DSH 初始固定 0.1.5-rc.2；已有确定性排序和 Fixed WebView2 直接复用。必要的上游升级单独测试。暂不引入 worktree 产品化、新压缩算法、RAG、多 Agent 调度、插件市场。

## 不变量

- 不自动从内网服务故障切换到外网；不默认上传源码、日志或诊断。
- 配置缓存参数不代表服务端采用；缓存字段缺失不是零；不承诺统一命中率。
- 任务期间变更不冒充 AI 独占修改；hash 不冒充可恢复备份。
- UI 与模型执行相同的 Project Action；信任限定配置内容与工作区，变更后重新信任；模型不能授权自己。
- 执行继承当前 DSH 权限，不以桌面工具绕过沙箱；恢复和重试不自动重复副作用。
- 前缀检查比较模型可见内容，正常新增内容和合法权限/规则变化不计为故障。
- 本地自检不能证明系统全局无出网，也不能证明内网目标机通过；未知保持未知。
- 原生对话历史由 DSH 管理；桌面保存扩展操作状态，不建立竞争的会话真相源。

### 下一阶段缓存适配核对

- 捆绑 DSH 的 pi-ai profile 已支持 `cacheRetention`，模型/连接 compat 支持 `cacheControlFormat`、`supportsLongCacheRetention`；应复用正式配置通路。
- 当前 pi-ai OpenAI Completions 在自定义地址上将 `prompt_cache_key` 与 long retention 条件耦合；`long` 还会发送 `prompt_cache_retention=24h`。因此不能把开启 long 当作“仅开启缓存键”，也不能在未知网关上自动开启。
- Anthropic 适配器已有原生 cache_control；默认 short，long 在支持时附带 1h TTL，不需要桌面重复注入。
- `GenerateOptions` 未暴露独立缓存键/原始 payload hook；下一阶段必须如实区分适配器可表达的配置和网关实际支持。探针需走原生 llm.stream，并分别呈现配置、实际请求契约、返回计数器与未知状态。以上是捆绑代码核对，尚非内网服务能力验证。
